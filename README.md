# ai-orchestrator

Личный конвейер делегирования для Claude Code. Главная (интерактивная) сессия думает и решает, а объёмную рутину выполняют дешёвые воркеры — через LLM-шлюз с моделями GLM/Grok/MiniMax или нативно на подписке Claude (Haiku/Sonnet). Результат возвращается выжимкой со ссылками `файл:строка` или патчем, который применяет человек.

Основная платформа — Windows + PowerShell 5.1. На macOS/Linux скрипты запускаются под pwsh 7 (см. [Установка](#установка)), но проверено это только частично.

Порт «схемы оркестратора» (исходная инструкция была под macOS/POSIX sh) на PowerShell.

## О чём этот проект — простыми словами

Вы работаете с Claude Code — это ИИ-ассистент, который помогает писать код прямо в терминале или VS Code. Проблема одна: ассистент «умный, но дорогой» — всё, что он читает (длинные логи, чужой код, большие файлы), оплачивается по тарифу самой мощной модели, и лимит подписки тает на глазах.

Этот проект — одна команда `ai-orch` с подкомандами-помощниками. Рутину они отдают дешёвым моделям, а дорогая занимается только сутью задачи:

- `ai-orch ask файл` — «перескажи, что здесь важно, и покажи где»: длинный файл превращается в короткую выжимку с номерами нужных строк;
- `ai-orch task scout "найди, где…"` — поиск и разведка в коде;
- `ai-orch task start "сделай черновик…"` — черновик правки, который вы потом сами проверите и примените;
- `ai-orch review` — «второй взгляд»: вашу правку проверяет модель другого семейства и замечает то, что автор пропустил.

Что для этого нужно: подписка Claude (Pro/Max) — помощники работают внутри неё и тратят лимит совсем медленно. Если есть ещё доступ к шлюзу hapy (сервер с дешёвыми моделями) — экономия и качество проверки становятся ещё лучше, но это не обязательно.

Как начать: [установите проект](#установка) (несколько минут), затем в обычном терминале наберите `ai-orch ask README.md` — и получите выжимку этого файла. Привычная работа с Claude Code не меняется: просто появляются новые команды. Список всех подкоманд — `ai-orch -h`.

## Зачем это нужно

Главная сессия работает на дорогой модели, и всё, что попало в её контекст, оплачивается на каждом следующем ходу: прочитали лог на 3000 строк — и он «висит» в контексте до конца сессии, умножаясь на каждый запрос. Оркестратор разрывает эту связку и экономит токены и деньги сразу по трём линиям:

- **Сырой материал не попадает в контекст основной сессии.** Логи, дампы, чужой код и большие диффы читает дешёвый воркер, а основная модель получает только выжимку на пару экранов со ссылками `файл:строка`. Файл на 50 КБ токенов превращается в выжимку на 2 КБ — контекстное окно живёт дольше, и каждый следующий ход дешевле.
- **Дешёвая модель на дешёвой работе.** «Найди, где в коде используется X», «перескажи этот конфиг», «черновик правки по готовой схеме» — это работа Haiku/GLM/MiniMax-класса, она в разы дешевле работы топовой модели. Платить за неё тарифом основной модели незачем.
- **Оплата идёт там, где дешевле.** На шлюзе работа воркеров тарифицируется по дешёвым моделям; на подписке Haiku жжёт общую квоту на порядок медленнее, чем жгла бы основная модель с тем же материалом в контексте.

Бонус не про деньги: **оппонент из другого семейства** (Grok/GLM против Claude-кода) ловит ошибки, к которым модель-автор слепа.

Итог: решения и приёмка — на дорогой модели; таскание материала — на дешёвых. Счёт за токены падает кратно, а окно контекста основной сессии расходуется только на суть задачи.

## Состав

Единая точка входа — `ai-orch <подкоманда>` (справка: `ai-orch -h` / `--help`, версия: `ai-orch -v`):

| Команда | Роль | Модель по умолчанию |
| --- | --- | --- |
| `ai-orch ask файл [файл…]` / `-Text` / stdin | digest: выжимка материала, ≤40 строк, ссылки `file:line` | glm-5.3-flash (шлюз) / haiku (нативно) |
| `ai-orch task scout "задача"` | разведка кода по снимку репозитория, только чтение | glm-5.3 (шлюз) / haiku (нативно) |
| `ai-orch task start "задача"` | черновик правки в снимке → патч в `patches/` | glm-5.3 (шлюз) / sonnet (нативно) |
| `ai-orch review -Spec … -Diff …` | оппонент: вердикт и замечания по ТЗ и/или диффу | авто: glm-5.3 (<8 КБ) / grok-4.7 (шлюз); sonnet (нативно) |
| `ai-orch mode hapy\|claude\|status` | переключение бэкенда **основной сессии** (после Reload Window) | — |
| `ai-orch stats [-Days 30] [-All]` | статистика моделей: сколько работы ушло через шлюз hapy, а сколько напрямую в Anthropic — по источникам (основная сессия, субагенты, воркеры, ask/review) и моделям | — |
| `ai-orch check` / `status` / `set-token` / `set-gateway` / `update` | сервис: проверка установки, последние вызовы воркеров, токен, адрес шлюза, обновления | — |

Подкоманда — простое слово без дефиса (`ai-orch update`): `-update`/`--update` параметрами PowerShell быть не могут, а `-h`, `--help`, `-v` — работают. Опции после подкоманды передаются ей как есть.

`ai-orch` — единственная команда в PATH. Каждая подкоманда — отдельный скрипт в `~/.claude/bin/ai-orch-lib/` (в репозитории — `bin/ai-orch-lib/`); эта папка в PATH не входит, поэтому подкоманды доступны только через `ai-orch`. Отдельные команды версий до 1.5 (`hapy-ask`, `glm-task`, `orch-check`…) удалены — установщик и `ai-orch update -Apply` убирают их из `~/.claude/bin`.

У `ask`, `review`, `task` есть `-Backend auto|gateway|claude`:
`auto` = шлюз, если в `~/.claude/settings.hapy.json` прописан env шлюза (адрес и токен без плейсхолдеров), иначе нативный `claude -p`. Режим `ai-orch mode` основной сессии оркестратору безразличен.

## Правила оркестрирования

1. **Асимметрия объёма и решения.** Делегируется то, где материала много, а решения мало: логи, выгрузки, чужой код, большие диффы, рутина. Вопросы, решения, приёмка, мелкие правки — основная сессия делает сама.
2. **Не делегируется никогда:** принятие решений, приёмка результатов, секреты (токены, ключи, пароли), общение с внешним миром (коммиты, пуши, деплой).
3. **Одна строка вслух.** Каждый вызов инструмента печатает, какая модель и какой бэкенд выбраны и сколько материала уходит («digest: haiku (backend: claude, material: 1352 chars)»).
4. **Выборочная проверка.** Ответ внешней модели не принимается на веру: 2–3 ссылки `файл:строка` открываются и сверяются. Воркер может ошибаться уверенно.
5. **Патч применяет человек** (или основная сессия по явной просьбе): `git apply --check` → `git apply`. Воркер никогда не касается рабочей копии.
6. **Оппонент — из другого семейства.** Ревью тем ценнее, чем сильнее модель оппонента отличается от автора кода. Нативный оппонент (Claude против Claude) — запасной вариант; если шлюз доступен, ревью идёт через него.
7. **Счётчикам токенов шлюза не верить** — они приблизительные; оплата идёт по факту на стороне шлюза.
8. **Решение и последняя инстанция — всегда у человека.** Воркеры возвращают черновики и мнения, не решения.

## Установка

Ставится всё силами Claude Code. Своими руками остаётся только то, что трогает секреты и настройки самого Claude Code: токен вводится в своём терминале (чтобы не проходил через чат), а запуск установщика защита прав иногда требует взять на себя — тогда Claude Code выдаст вам готовую команду. Ничего готовить заранее не нужно: если у вас есть шлюз, Claude Code сам спросит про него (и адрес) в чате по ходу установки. На новой машине откройте Claude Code в любом каталоге и напишите ему:

> Установи оркестратор из https://github.com/S1mkin/ai-orchestrator — следуй файлу INSTALL.md в репозитории.

Дальше по [INSTALL.md](INSTALL.md) он сам:

1. проверит окружение (Windows: PowerShell есть из коробки; macOS/Linux: pwsh 7 и Git) и спросит, куда клонировать репозиторий;
2. спросит в чате, есть ли у вас шлюз, и если есть — попросит адрес (это не секрет, чат подходит) и сразу впишет его в конфиги; токен попросит ввести вас самих командой `ai-orch set-token` в вашем терминале — он не попадает ни в чат, ни в историю сессии (можно и вовсе без шлюза: `-NoToken`, останется нативный бэкенд на подписке; быстрый путь «токен в чате» — только если вы сами так решите);
3. запустит `install.ps1` (если защита прав не даст агенту менять `~/.claude` — вручит вам готовую команду для терминала, это нормальная работа защиты): скрипты уйдут в `~/.claude/bin` (PATH обновится; на macOS Claude Code пропишет PATH и алиасы в `~/.zshrc`), профили воркеров — в `~/.claude-glm` и `~/.claude-worker`, варианты настроек — в `~/.claude/settings.hapy.json` и `settings.claude.json`; адрес подставится вместо плейсхолдера `__HAPY_BASE_URL__`, токен — шагом 2. Повторный запуск безопасен: уже настроенные файлы не перезаписываются, снимки и патчи не трогаются;
4. проверит результат командой `ai-orch check` (при желании с `-Live` — короткий запрос к шлюзу) и напомнит про новый терминал: в VS Code достаточно нового терминала PowerShell — установщик добавляет строку в профиль; если команды не видны — полностью перезапустите VS Code.

Требования: Windows или macOS/Linux, Git, VS Code с расширением Claude Code (или `claude` в PATH); для нативного бэкенда — подписка Claude (Pro/Max) с разовым входом `claude` → `/login`.

Как узнавать об обновлениях и ставить их — [Обновление](#обновление). Совсем без агента тоже можно: `git clone` + `install.ps1` — параметры перечислены в шапке `install.ps1` и в [INSTALL.md](INSTALL.md).

## Обновление

Версия зашита в сами скрипты и видна в `ai-orch -v` (и в выводе `ai-orch check`). Проверка и установка обновлений — одной командой на любой машине:

```powershell
ai-orch update           # сравнить установленную версию с GitHub (ничего не меняет)
ai-orch update -Apply    # обновить: git pull в клоне + переустановка скриптов
```

`ai-orch update` ходит на GitHub за свежей версией, `-Apply` подтягивает клон (установщик запоминает его путь) и переустанавливает скрипты — настроенные файлы с адресом/токеном не перезаписываются. Важно: `git pull` в клоне сам по себе установленные скрипты в `~/.claude/bin` не обновляет — их копирует только `-Apply`. Работает и через Claude Code: просто попросите «проверь обновления оркестратора» или «обнови оркестратор» — он выполнит `ai-orch update` и доложит результат. Без интернета проверка честно скажет, что не смогла сравнить.

## Шлюз hapy на новой машине

hapy — LLM-шлюз с Anthropic-совместимым API: Claude Code говорит с ним как с обычным Anthropic-сервером, а тот проксирует запросы к моделям GLM/Grok/MiniMax. Подключение на машине, где шлюз никогда не использовался, — два независимых шага: первый достаточен для оркестратора, второй (по желанию) переводит на шлюз саму основную сессию.

**Что понадобится:** адрес шлюза (`https://…`) и персональный токен вида `hapy_…` — их выдаёт администратор шлюза или личный кабинет. Нет токена — оркестратор всё равно работает: скажите Claude Code ставить без шлюза (`-NoToken`) и используйте `-Backend claude`.

**1. Воркеры через шлюз.** Адрес и токен попадают в конфиги либо сразу при установке (`install.ps1 -BaseUrl … -Token …`), либо по отдельности потом: `ai-orch set-gateway -BaseUrl …` задаёт адрес, `ai-orch set-token` спрашивает токен в терминале. Правятся два файла: `~/.claude/settings.hapy.json` (конфиг шлюза для воркеров ask/review) и `~/.claude-glm/settings.json` (профиль воркеров task). Основная сессия при этом не меняется. Проверка: `ai-orch ask README.md` — в строке статуса должно быть `backend: gateway`.

**2. Основная сессия через шлюз (по желанию).** `ai-orch mode hapy` — настроенный вариант копируется в живой `~/.claude/settings.json` (env `ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN`, модель по умолчанию `glm-5.3`, список моделей для `/model`), затем Reload Window (Ctrl+Shift+P). Теперь и основная сессия идёт через шлюз — модели GLM/Grok/MiniMax, оплата по тарифам шлюза, а не по подписке. Вернуться на встроенные модели: `ai-orch mode claude` + Reload Window. Текущий режим подскажет `ai-orch mode status`.

Токен после установки хранится в `settings.hapy.json` и `~/.claude-glm/settings.json`, а после шага 2 — ещё и в живом `settings.json`. Ротация — двумя отдельными командами: `ai-orch set-token` спросит новый токен прямо в терминале (в pwsh ввод замаскирован; вариант `-Token <новый>` — для скриптов) и обновит его во всех файлах, где он есть; `ai-orch set-gateway -BaseUrl <адрес>` сменит адрес (адрес — не секрет, её можно запускать и из скриптов/агента). Проверка после: `ai-orch check -Live`.

## Как устроено

- **Шлюзовой бэкенд:** HTTP SSE на `/v1/messages` шлюза (стриминг обязателен — без него длинные генерации падают с 504). Адрес и токен читаются из `settings.hapy.json` при каждом вызове; в репозитории вместо них плейсхолдеры.
- **Нативный бэкенд:** безголовый `claude -p` в изолированном профиле `~/.claude-worker`. Подписной логин в изолированный профиль сам не виден, поэтому раннер при каждом запуске копирует туда свежий `~/.claude/.credentials.json`; токена шлюза в этом профиле нет.
- **Изоляция воркеров задач** (`ai-orch task`): работа только в снимке `git archive HEAD`; секретные файлы (`.env`, `config.inc.php`, ключи…) удаляются из снимка; контент-скан на секретоподобные строки — при любом совпадении запуск отменяется, а совпадения печатаются маской (первые 4 символа); хук PreToolUse `guard-paths.ps1` в профилях воркеров не выпускает файловые инструменты (Read/Grep/Glob/Edit/Write) за пределы снимка, а в Bash пропускает только `git status/log/show/grep` без выхода из снимка — сам Claude Code разрешает читать любые пути и запускать `cat`/`ls` где угодно, deny-правилами это не закрыть; поверх хука — deny на `~/.ssh`, `~/.claude`, файлы с токеном/логином воркеров, push/commit/сеть/`rm`/WebFetch/WebSearch. Установщик обновляет права и хук и в уже настроенном профиле, не трогая адрес и токен, а `ai-orch check` проверяет, что хук действительно блокирует; канон (`CLAUDE.md`/`AGENTS.md`) только для чтения. OS-песочницы на родном Windows нет — стены прикладные.
- **Секреты наружу не идут и не возвращаются:** материал выжимки/ревью сканируется перед отправкой, а ответ воркера — перед выводом в консоль; при совпадении вывод маскируется, полный текст остаётся файлом внутри снимка. Токен шлюза при установке и ротации вводится командой `ai-orch set-token` в терминале пользователя и через чат/агента не проходит; адрес шлюза — не секрет, его задаёт `ai-orch set-gateway`.

## Настройка под себя

- промпты digest/opponent: `profiles/glm/prompts/*.txt` (после установки — `~/.claude-glm/prompts/`);
- порог авто-выбора модели ревью (8 КБ) и сами модели: `bin/ai-orch-lib/review.ps1`;
- allow/deny воркеров: `profiles/*/settings.json`;
- список исключений контент-скана `$scanExclude` в `bin/ai-orch-lib/task.ps1` — сейчас настроен под проект с MODX (публичный дистрибутив исключён, свой код сканируется); под другой проект скорректируйте;
- лог использования: `~/.claude/orch-usage.tsv` — каждая команда воркера дописывает строку (роль, модель, размер материала, токены); сводка — `ai-orch status`. В лог не попадает ни промпт, ни материал, ни ответ.
- статистика моделей — `ai-orch stats`: читает локальные журналы сессий Claude Code (`~/.claude/projects`, `~/.claude-glm/projects`, `~/.claude-worker/projects` — там точные токены каждого ответа модели) и лог оркестратора (ask/review через шлюз идут прямым HTTP-запросом без журнала). Маршрут определяется по модели: `claude-*` — напрямую в Anthropic, остальные (GLM/Grok/MiniMax) — через шлюз; воркеры `task` профиля `~/.claude-glm` — всегда шлюз. Колонки: свежий ввод, чтение и запись кэша промпта, вывод; доли — по выводу (сгенерированная работа) и по всем токенам. Ничего никуда не отправляется.

## Ограничения

- Основная платформа — Windows + PowerShell 5.1. macOS/Linux: через pwsh 7, шлюзовой бэкенд должен работать, нативный не проверялся.
- Команды — PowerShell-скрипты: из PowerShell (включая pwsh) запускаются напрямую, из чистого `cmd.exe` — нет (понадобятся .cmd-обёртки, в комплект не входят).
- `ai-orch mode` меняет env основной сессии только после перезагрузки окна VS Code.
- Встроенный терминал VS Code наследует окружение процесса VS Code, снятое при его запуске: сразу после установки команд может не быть. Установщик лечит это строкой в профиле PowerShell (каждый новый шелл дописывает `~/.claude/bin` в PATH сам); если не помогло — полный перезапуск VS Code.
- Нативные воркеры тратят ту же квоту подписки (окна 5 ч / неделя), что и основная сессия — экономия в том, что Haiku жжёт её на порядок медленнее, а сырой материал не попадает в контекст основной сессии.
- Контент-скан эвристический: бывают ложные срабатывания (файл или каталог добавляют в исключения/чистку) и, теоретически, пропуски. Это стена от случайности, а не защита от целенаправленной эксфильтрации.
